Living implementation plan

HanabiCode fork and release plan

Keep Dey11/paseo easy to update from getpaseo/paseo, while shipping a separate HanabiCode desktop app, Android app, native VPS daemon, state directory, updater, and release history.

Current state

The local hanabicode branch contains upstream commit adf80a9fe through merge commit ac565b0b2. The fork keeps its standalone identity and hosted-Hub boundary while taking the latest upstream features.

The fork identity, independent 0.1.x version line, tag-driven release workflow, Android signing contract, native ARM64 daemon bundle, rootless installer, and relay configuration boundary are implemented. The current release uses the official Paseo relay over TLS, keeps Tailscale recovery, and accepts a future fork-owned endpoint. The Android signing secrets are configured in the protected GitHub environment. No HanabiCode release has been published yet.

Daemon and remote connectivity answer

Yes, release the daemon from the fork

App and daemon versions drift in normal use, so the fork must own both. The desktop build already bundles the daemon. The release pipeline also publishes a native Linux ARM64 archive from the same tag for the VPS.

Do not publish the upstream @getpaseo/* npm packages. That namespace is not the fork's release channel, and the desktop and container do not need public npm publication. The native builder packs those workspaces directly into the archive.

Now, use the official relay; self-host it later

Point the release daemon and pairing offers at relay.paseo.sh:443 over TLS. The client and daemon keep application frames end-to-end encrypted, and the VPS needs no public inbound port.

Keep Tailscale as a saved direct recovery path. The installer accepts a relay endpoint and TLS policy so a future deployment can move to a fork-owned hostname without a product code change.

The future deployment uses the Elixir service from getpaseo/paseo-relay. The Cloudflare Durable Objects adapter in this monorepo is legacy code, not the production relay.

Implementation phases

Phase 0

Stabilize the merged branch

  • Audit every conflict-sensitive fork feature after the -X theirs upstream merge, especially port forwarding, product identity, desktop startup, daemon state, and updater behavior.
  • Keep upstream's newer implementation when a fork change only renamed an internal symbol.
  • Retain fork changes only at product boundaries and in intentional opinionated features.
  • Regenerate package-lock.json from the merged manifests and confirm npm ci succeeds from a clean checkout.
Phase 1

Normalize the fork boundary

  • Replace fork release, updater, source, issue, and documentation URLs with https://github.com/Dey11/paseo.
  • Change fork-doc branch links from main or personal to hanabicode.
  • Keep upstream links only where the text is genuinely about official Paseo.
  • Resolve the current Apache versus AGPL documentation mismatch before distribution. Preserve upstream copyright and license notices either way.
  • Replace upstream artwork before sharing builds publicly, or get explicit permission to use it.
Phase 2

Give HanabiCode its own version and tag rules

  • Set the first release line to 0.1.0 and sync every workspace manifest.
  • Add a fork release script that uses the existing version calculator but creates tags with the hanabicode-v prefix.
  • Support stable tags such as hanabicode-v0.1.0 and beta tags such as hanabicode-v0.1.1-beta.1.
  • Disable or remove fork-facing scripts that publish @getpaseo/* to npm. Keep dry pack checks as verification.
  • Make the release validator require that the tagged commit belongs to origin/hanabicode.
Phase 3

Build one draft-first GitHub release

The hanabicode-release.yml workflow should run on a hanabicode-v* tag push. Manual dispatch remains a retry tool, not the primary release trigger.

  1. Validate tag syntax, source branch ancestry, and matching package versions.
  2. Create a draft GitHub release in Dey11/paseo.
  3. Run formatting checks, lint, typecheck, focused release tests, and package dry runs.
  4. Build macOS ARM64 and x64 DMGs and ZIPs with ad-hoc signing.
  5. Build one universal, release-signed Android APK with Gradle.
  6. Build a self-contained HanabiCode-X.Y.Z-linux-arm64.tar.gz archive on GitHub's Ubuntu 22.04 ARM64 runner. Include Node, the daemon web UI, production dependencies, licenses, source metadata, and the rootless installer.
  7. Merge updater manifests, add checksums, include LICENSE and NOTICE, then publish the draft only after required jobs pass.

Windows, Linux desktop, iOS, Play Store, App Store, website deployment, and npm publication stay outside the first release.

Phase 4

Set up Android signing once

  • Create a permanent PKCS#12 signing key on a trusted machine.
  • Keep two offline backups. Losing this key prevents an APK from updating an installed copy.
  • Create a protected GitHub environment named release.
  • Store ANDROID_KEYSTORE_BASE64, ANDROID_KEYSTORE_PASSWORD, ANDROID_KEY_ALIAS, ANDROID_KEY_PASSWORD, and ANDROID_CERT_SHA256 as environment secrets.
  • Have Actions verify the APK signature and expected SHA-256 certificate before upload.
Phase 5

Keep macOS installable now, notarize later

  • Build ad-hoc-signed artifacts with no Apple secrets.
  • State the Gatekeeper override in release notes and installation docs.
  • Verify the app's bundle ID, signature structure, daemon bundle, updater manifest, CLI, state directory, and side-by-side installation with official Paseo.
  • When an Apple Developer ID is available, add certificate and notarization secrets, turn on hardened runtime, and make Gatekeeper assessment a release gate.
Phase 6

Prove the rootless native daemon package

  • Build the archive on GitHub's Ubuntu 22.04 ARM64 runner and include the exact Node runtime used for the build.
  • Run the archive acceptance test under an isolated temporary home. Load node-pty, exercise the installed CLI symlink, and inspect the generated systemd unit.
  • Install releases under ~/.local/share/hanabicode/releases and switch an atomic current symlink. Never start or restart the daemon from the installer.
  • Keep state in ~/.hanabicode, bind to the exact Tailscale address on port 6769, enable relay.paseo.sh:443 over TLS, and run as a user systemd service.
  • Promote or roll back manually by selecting a release and explicitly restarting the service after active agents are safe to interrupt.
Phase 7

Cut the first beta, then stable

  1. Cut hanabicode-v0.1.1-beta.1 from a reviewed hanabicode commit.
  2. Install both macOS architectures where hardware is available, install the APK on the target Android phone, and run the native daemon archive on the VPS.
  3. Test clean install, pairing, reconnect, app restart, terminal traffic, agent control, Files, Ports, and update continuity.
  4. Fix failures on the branch and cut a new beta tag. Never move an existing tag.
  5. Cut hanabicode-v0.1.0 only after upgrade tests pass.
Phase 8

git merge --no-ff main

Merge upstream frequently while the patch stack is manageable. Do not rebrand internal package names. Keep each HanabiCode opinion in a focused commit so a future conflict points to one real product decision.

Phase 9

Deploy and prove the fork-owned Paseo relay

  • Keep the official relay and Tailscale as known-good paths during migration.
  • Select a fork-owned hostname, deployment target, TLS termination, monitoring, and backup policy before creating hosted resources.
  • Deploy the production Elixir implementation from getpaseo/paseo-relay. Do not promote the legacy Cloudflare adapter from packages/relay into production.
  • Verify pairing, reconnect, terminal binary frames, agent streams, file transfers, Android background/resume, long-thread loading, and Ports over long-lived relay WebSockets.
  • Reinstall the daemon with the fork-owned endpoint and create new pairing offers. Existing pairing offers keep their original relay endpoint.
  • Retain the official relay until the self-hosted service passes the full matrix, then remove that hosted dependency in a separate promotion.

Release gates

Blocks the first shared release

  • All Dey11/paseo release and updater references are removed.
  • Independent version and hanabicode-v* tag handling work.
  • Android signing key is backed up and configured.
  • Artwork and licensing are settled.
  • No workflow can publish to official Paseo targets.
  • macOS, Android, and daemon upgrade paths pass.

Can wait

  • Apple notarization
  • Play Store and App Store distribution
  • Windows and Linux desktop release assets
  • Expo/EAS and push notifications
  • Public website deployment
  • Fork-owned Paseo relay deployment
  • Cloudflare Tunnel alternative

What the finished setup looks like

main mirrors upstream. hanabicode carries a small, explicit product patch stack plus opinionated features such as port forwarding. A hanabicode-v* tag builds the exact tagged commit, leaves a draft while checks run, and publishes macOS, Android, checksums, source notices, and a native ARM64 daemon archive. Every updater and source link stays inside Dey11/paseo.

The macOS app and Android app pair with the same fork daemon. The desktop can also run its bundled daemon locally. Remote access uses the official Paseo relay over TLS with Tailscale as recovery. A later infrastructure phase moves the same protocol to a fork-owned relay endpoint. Upstream code remains useful without owning HanabiCode's identity, releases, state, signing keys, or future infrastructure.

Status: release implementation and Android signing setup are complete. Branch push, release tag, artifact publication, device installation, VPS promotion, and the future self-hosted relay remain activation steps.
